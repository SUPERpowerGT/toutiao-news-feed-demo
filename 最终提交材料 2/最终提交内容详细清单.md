## 3. 最终实习交付物 ZIP

提交文件名：

`<TeamXX - Final deliverables>.zip`

提交内容：

| 序号 | 文件名 | 文件类型 | 需要包含什么 | 详细解释 |
| --- | --- | --- | --- | --- |
| 1 | `TeamXX - Final Internship Project Report.docx` | Word 报告 | 完整项目报告 | 没有统一模板，但必须覆盖指南要求的所有章节和工件。报告应系统性证明项目背景、需求、架构、设计、实现、测试、DevSecOps、安全、管理过程和价值增量。优秀报告通常超过 50 至 100 页。 |
| 2 | `TeamXX - Presentation Deck.pptx` | PowerPoint | 最终展示 Deck | Deck 应与视频内容一致，覆盖管理、架构、软件设计、DevSecOps、价值增量和 Demo 说明。它是视频展示的结构化支撑材料，也方便评审快速定位证据。 |

最终报告建议章节：

| 章节 | 需要回答的问题 | 建议放入的证据 |
| --- | --- | --- |
| 项目背景与目标 | 为什么要做这个项目？解决什么业务痛点？带来什么收益？ | 背景说明、痛点分析、目标定义、Sponsor 价值 |
| 需求与范围 | 项目包含哪些功能、用例和边界？哪些不在范围内？ | Use Case Diagram、Scope、Product Backlog、User Stories |
| 项目管理 | 团队如何使用敏捷方式推进？投入是否可追踪？ | Sprint Plan、Sprint Backlog、Burndown Chart、任务看板、工时记录、Sprint Review/Retrospective |
| 架构设计 | 系统如何拆分？关键架构决策是什么？为什么这样设计？ | 逻辑架构图、物理架构图、部署图、DDD 图、架构约束、架构风险和缓解 |
| 软件设计 | 关键用例如何实现？类和对象如何协作？ | 类图、顺序图、关键流程说明、设计模式、数据模型 |
| 数据设计 | 数据如何建模、存储和流转？ | DB schema、NoSQL collection objects、ER 图、数据流图 |
| DevSecOps | 如何自动化构建、测试、扫描、部署？ | CI/CD 图、Pipeline 日志、测试结果、SAST/DAST 结果、容器扫描、IaC、Git history |
| 测试与质量 | 如何证明系统质量？覆盖了哪些测试类型？ | 单元测试、集成测试、端到端测试、压力测试、测试用例和结果 |
| 安全设计 | 威胁是什么？如何缓解？ | Threat model、安全控制、扫描结果、漏洞修复记录 |
| Demo 与结果 | 系统最终做到了什么程度？是否上线或被接受？ | App Demo 截图/链接、运行结果、Sponsor 反馈、上线证据 |
| 价值增量 | 相比最低要求，额外价值在哪里？ | AI/数据分析/实时处理/创新能力说明、业务指标、技术收益 |
| 反思与改进 | 项目有哪些问题、风险和后续计划？ | 已解决问题、未解决风险、后续 roadmap |

## 5. 代码工件与 Repo URL

| 内容 | 是否必须 | 详细解释 |
| --- | --- | --- |
| Code Artifacts | 是 | 用于证明项目真实完成，不能只靠文字描述。可以包括源码、关键模块截图、构建脚本、配置文件、测试代码、部署配置等。 |
| Repo URL | 是 | 提供代码仓库链接，方便评审查看 Git history、代码结构、贡献记录和工程实现。 |
| 无法提交源码的说明邮件 | 条件必须 | 如果因为公司保密或权限原因不能提交源码，需要让 supervisor 给 Internship Manager 发邮件说明。注意：PDF 和邮件都强调“Confidentiality 不是不展示证据的理由”，因此仍需提供可接受的替代证据。 |

可替代或补充的证据包括：

- 关键代码片段截图。
- 模块结构图。
- Pull Request 或 commit 记录。
- CI/CD 执行记录。
- 测试报告。
- 安全扫描报告。
- Demo 视频。
- Sponsor 确认或反馈。

## 6. 最容易漏掉的内容

| 易漏项 | 为什么重要 | 建议处理 |
| --- | --- | --- |
| 类图和顺序图 | Software Design 明确要求关键用例达到类/对象级设计 | 至少选 1 个复杂或架构重要用例画完整类图和顺序图 |
| DDD 图 | Architecture Assessment 明确要求 Domain Driven Design diagrams | 用 bounded context、domain model 或上下文映射说明业务边界 |
| 物理架构和网络细节 | 不能只给逻辑架构总览 | 补充部署节点、网络连接、基础设施组件和环境说明 |
| SAST/DAST 修复后重扫结果 | DevSecOps 不只看扫描，还看漏洞修复闭环 | 保留初扫结果、修复说明和 rescan 结果 |
| Burndown Chart 和工时对比 | Management Assessment 要求项目执行证据 | 从 JIRA 或其他工具导出截图/图表 |
| Sponsor 接受或上线证据 | Value Added Assessment 中明确提到 preferably going live | 准备 sponsor 邮件、反馈截图、上线说明或试运行证明 |
| 每位成员参与视频 | 超过 1 人团队要求每位成员参与视频制作 | 提前分配每个视频的讲解人，避免最后录制不均 |
