## **一、数据层架构重构与健壮性提升**

本次迭代的核心目标是：
 **让数据层结构更符合 Clean Architecture 标准，并解决 API 返回格式与客户端结构不匹配导致的解析问题。**

### **1. 统一 API 响应包装结构**

**调整内容：**

- 新增 `ApiResponse<T>` 泛型包装类。
- `FeedApiService` 改为返回 `ApiResponse<FeedResponseDto>`。

**解决问题：**

- 解决了之前 `FeedResponseDto` 无法解析包含 `code/message/data` 的完整 JSON 结构的问题。
- 规范了网络层返回格式，让所有 API 都遵守统一包装结构。

**本质原因：**

- 项目缺失基础的 API 状态包装层。

------

### **2. 修正 DTO 字段类型，使其与后端严格匹配**

**调整内容：**

- `FeedResponseDto.nextCursor` 类型由 `String?` 修正为 `Long?`。

**解决问题：**

- 解决了客户端/后端类型不一致导致的解析异常。
- 避免 `next_cursor: 1764559743` 这种本为数字却被解析成字符串的问题。

**本质原因：**

- DTO 定义时未严格遵守后端返回类型。

------

### **3. 在 RemoteDataSource 添加统一的 API 状态检查机制**

**调整内容：**

- 在 `RemoteDataSource` 对 ApiResponse 做 `code==0` 校验。
- 自动解包 `data` 字段，统一错误处理。

**解决问题：**

- 解决了 Repository 与 ApiService 返回类型不一致导致的编译报错（Return Type Mismatch）。
- Repository 不再需要关心网络状态，只接收“已经解包过的干净数据”。

**本质原因：**

- 网络细节不应泄露到 Repository 层。

------

### **4. 为统计字段添加明确的 @SerializedName 注解**

**调整内容：**

- 为 `StatsDto` 中 `likeCount/commentCount/...` 等字段显式声明 JSON key。

**解决问题：**

- 解决部分数据在 snake_case → camelCase 自动转换失败时解析不到的问题。

**本质原因：**

- Gson 对 snake_case 自动转换不完全可靠，需显式声明。

------

### **数据层重构最终效果总结**

通过以上修改：

- **RemoteDataSource → 完全负责 API 结构和状态处理**
- **Repository → 只接收干净业务数据 FeedItem 列表**
- **Domain 层 → 不再承担 JSON/状态校验等非职责逻辑**

数据链路成功向 Clean Architecture 靠近，模块职责更明确、错误更易定位。

## **二、首页 Feed 卡片渲染性能优化**

首页推荐流同时包含大量图文/视频封面，首屏极易出现掉帧/卡顿。
 本次优化针对 **“图片开销过大 + Compose 渲染过载”** 两大瓶颈做了系统性优化。

------

### **1. 限制封面图的解码 size，降低单张图片的 decode 成本**

**实现方式：**

- 封装 `CardCoverImage` 组件。
- 使用 Coil `.size(widthPx)` 限制解码像素（约 200–300px）。

**效果：**

- 避免解码原始 800x600 甚至更大的图片。
- 单张图片内存消耗显著下降，减少 OOM 风险和解码时间。

**核心意义：**

- 让图片“按需解码”，避免 GPU/CPU 峰值过载。

------

### **2. 精简卡片布局结构，减少 Compose LayoutPass 与重绘成本**

**实现方式：**

- 重构 ImageCard / VideoCard 为统一的结构：
  - Column → Row(标题+封面) → Row(作者/操作) → Divider
- 把重复区域（作者信息、按钮）抽离成可复用组件。

**效果：**

- 每个卡片的布局节点数量显著减少。
- 布局测量次数下降，滚动更稳定。
- 减少多重 Box/Column 嵌套引发的深层 LayoutPass。

**核心意义：**

- 降低 Compose UI 在大列表下的整体计算压力。

------

### **3. 按需懒加载（今日头条式渲染策略），避免一次性加载过多卡片**

**实现方式：**
 在 `FeedList` 中：

```
val shouldRender = 
    index < 6 || listState.firstVisibleItemIndex >= index - 1
```

不渲染 → 显示轻量级 Spacer
 靠近可视区域 → 才真正执行 `FeedCardFactory`

**效果：**

- 首屏只渲染前 6 条，避免一次性加载 20+ 卡片导致的严重掉帧。
- 滚动时按需加载，不会造成瞬间 CPU/GPU 峰值。

**核心意义：**

- 拉平计算量峰值，保持滑动流畅度。

------

# **三、整体效果总结**

通过“数据层重构 + UI 渲染层优化”的组合拳，本次迭代实现了：

### **数据层**

- API 响应处理标准化
- DTO 结构与后端一致
- 错误处理统一
- Repository 更纯净

### **UI/性能层**

- 单张图片 decode 成本降低
- 大量卡片的布局复杂度下降
- 首页首屏不卡顿（避免一次性渲染 30+ 卡片）
- 滑动稳定、掉帧显著减少

整体系统的**稳定性、扩展性、性能**均得到明显提升。
