#  FeedCardFactory 架构升级说明（维护记录 1）

## 📌 背景问题（升级前的痛点）

原始版本的 `FeedCardFactory` 依赖 **字符串 newsType** 手动判断：

```
when (item.newsType) {
    "text" -> TextCard(...)
    "image" -> ImageCard(...)
    "video" -> VideoCard(...)
}
```

在初版 Demo 中能跑，但存在明显的工程问题：

### ❌ 1. 可扩展性极差

每新增一个 UI 卡片类型，都需要：

- 后端加字段
- DTO 加字段
- 数据库加字段
- 前端再写 if/when
- 再通过字符串硬编码判断类型

这是一条“改一次，五处爆炸”的链路。

### ❌ 2. 类型完全不受 Kotlin 编译器保护

- 用字符串拼错就崩
- IDE 不会补全
- 无法被编译器检查
- Bug 不可见、不可预测

这在一个多卡片体系（推荐流典型包含 10～40 种卡片）里几乎一定会导致长期维护地狱。

### ❌ 3. 卡片类型没有统一抽象

你后面会遇到：

- isOfficial → 官方媒体置顶卡
- isTop → Top 标题卡
- hasManyImages → 三图卡
- isPinned / isAds → 广告卡
- isSpecial → 活动卡、视频合集卡、图文混排卡…

如果继续依赖 newsType，你的 Feed 体系会越来越破碎。

------

# 🔧 升级后的方案：使用 **sealed class FeedCardType**

### ✔ 1. 明确卡片的类型系统（强类型体系）

```
sealed class FeedCardType {
    data object Text : FeedCardType()
    data class SingleImage(val ratio: Float) : FeedCardType()
    data object ThreeImage : FeedCardType()
    data object Video : FeedCardType()
    data object OfficialTop : FeedCardType()
    data object Ad : FeedCardType()
}
```

优势显著：

- **IDE 自动补全**
- **新增类型必须显式实现 → 编译期强制检查**
- **类型安全，不会字符串拼错**
- **数据结构表达更丰富（如 ratio、meta、样式）**

------

# 🔁 FeedCardFactory 升级后（大厂级写法）

```
@Composable
fun FeedCardFactory(
    item: FeedItem,
    modifier: Modifier = Modifier
) {
    when (val type = item.cardType) {
        is FeedCardType.Text -> TextCard(item, modifier)
        is FeedCardType.SingleImage -> SingleImageCard(item, type.ratio, modifier)
        is FeedCardType.ThreeImage -> ThreeImageCard(item, modifier)
        is FeedCardType.Video -> VideoCard(item, modifier)
        is FeedCardType.OfficialTop -> OfficialTopCard(item, modifier)
        is FeedCardType.Ad -> AdCard(item, modifier)
    }
}
```

### 🌟 升级亮点

- 新卡片类型“必须”被处理，否则无法编译
- 开发 IDE 自动提示所有卡片类型
- 卡片类型信息可以包含参数，如 ratio、layout、actions
- 可在 usecase 内统一规则（如官方媒体置顶）

# 📚 设计升级原因（从 Demo → 大厂级）

这是你架构升级中最重要的地方，体现你的思考深度。

## 🎯 1. 解决“字段爆炸问题”

原先你的思路：

👉 cardType = newsType
 👉 官方卡？加 isOfficial
 👉 置顶卡？加 isPinned
 👉 广告？再加 isAd
 👉 活动卡？再加 isEvent

最终必然会导致：

**字段爆炸 → 后端/前端维护地狱**

大厂不会这样做。
 大厂统一使用：

> **((业务属性) → 使用 usecase 决策 → 输出卡片类型) → UI 渲染**

你现在正是实现了这一点。

------

## 🎯 2. 建立“渲染策略清晰化（Render Strategy）”

你现在的设计本质是：

### “数据是什么”

和

### “UI 用什么卡片展示”

**彻底解耦**

也就是：

> FeedItem → ProcessFeedItemsUseCase → FeedCardType → FeedCardFactory

一个完整的策略链路：

1. DTO 中原始字段：是否官方、媒体类型、图片数量、视频元数据
2. UseCase 统一决策：这是三图卡还是官方卡
3. UI 渲染层只看 cardType，不看原字段

这和头条、抖音、微博的架构一致。

------

## 🎯 3. 提升 Feed 架构的内聚性、稳定性与可测试性

升级前：

- 很难做 UI 单测
- 逻辑散在 ViewModel、CardFactory、DTO 等处
- 新增卡片要动 5 个地方

升级后：

- cardType 决策全部集中在 UseCase（高内聚）
- UI 渲染层只画 UI（纯函数，可测试）
- 新卡片增量开发不再影响老代码（开闭原则 OCP）

你已经在遵循 **Clean Architecture + UI Render Strategy** 的原则。

# 🚀 FeedList + 渲染链路整体升级

## 升级前链路（存在大量隐式逻辑）

```
raw api → dto → feedItem(newsType=string) → FeedCardFactory → UI
```

存在的问题：

- newsType 决策分散，不统一
- 逻辑不透明
- 难以做“官方卡置顶”“三图卡识别”“视频卡增强”

------

## 升级后链路（大厂推荐流架构）

```
RawFeedDto
    ↓ mapping
FeedItem(raw model)
    ↓ ProcessFeedItemsUseCase（统一决策卡片类型）
FeedItem(cardType: FeedCardType)
    ↓
FeedCardFactory（选卡片渲染策略）
    ↓
Compose UI
```

特点：

- Render Strategy 独立
- UseCase 可复用、可测试
- 新类型扩展不再破坏现有逻辑
- 逻辑层→展示层清晰分层
